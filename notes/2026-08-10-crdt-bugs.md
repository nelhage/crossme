# CRDT audit findings (2026-08-10)

Audit of the CRDT merge implementations and sync layer: `crdt/merge.go`,
`client/src/crdt/merge.ts`, the live client-state merge (`mergeFill` in
`client/src/crossword.ts`), and the sync paths in `server/server.go` and
`client/src/components/puzzle.tsx`.

**Headline:** the two `merge` implementations match each other closely — but the
client doesn't actually use its `merge.ts`. The live client path applies server
updates through a separate, weaker merge (`mergeFill`), and that's where the
real divergences live. There is also one straight-up server crash bug.

## 1. Server panic: double-unlock in `broadcastFill` (bug)

`server/server.go:173-178` takes `game.Lock()` with `defer game.Unlock()`, then
on a merge error calls `game.Unlock()` explicitly and returns — so the deferred
unlock runs on an already-unlocked mutex and panics. A merge error is reachable
from any client (e.g. a fill whose cell `owner` index is out of range), so a
malformed `UpdateFill` request crashes the whole server. Fix: drop the explicit
`Unlock()`.

## 2. The live client merge (`mergeFill`) diverges from the canonical CRDT (logical bug, the big one)

`client/src/crdt/merge.ts` is a faithful port of the Go merge and is
cross-tested against shared vectors — but nothing imports it except its own
test. The code that actually applies incoming fills is `mergeFill` at
`client/src/crossword.ts:171-214`, which implements only plain LWW plus sticky
`DID_CHECK`/`DID_REVEAL`. It's missing two of the three special rules:

- **No "CHECKED_RIGHT always wins" rule.** In the canonical merge
  (`crdt/merge.go:106-113`), a checked-correct cell beats any later write. In
  `mergeFill`, a higher-clock plain write beats it. Concrete divergence: player
  A reveals a cell (clock 5, `CHECKED_RIGHT`); player B concurrently types a
  wrong letter there (clock 7). The server keeps the revealed letter, but every
  subscribed client applies B's raw delta via `mergeFill` and shows B's wrong
  letter. Server and all clients now permanently disagree until reload.
- **`checked` state is set but never cleared** (`crossword.ts:204-207`). The
  canonical merge takes `CHECKED_RIGHT|CHECKED_WRONG|PENCIL` from the winning
  cell, so overwriting a checked-wrong cell clears the wrong-mark. `mergeFill`
  only ever sets `checked`, so a stale `WRONG` marker survives an overwrite —
  and combined with the previous bullet, the reveal scenario above leaves a
  cell displaying B's wrong letter *while marked checked-correct*.
- **`fill.complete` is ignored entirely.** Partially compensated by the
  `nextError === undefined` guard in `withUpdate` (`crossword.ts:221`), but
  that only protects a client whose own grid is already correctly solved.

The clean fix is probably to make the client's canonical state a `pb.Fill`
merged via the existing (correct, tested) `merge.ts`, and derive the view-model
from it, rather than maintaining parallel merge semantics in `mergeFill`.

Related: because the server broadcasts the client's **raw delta**
(`server.go:186`) rather than the canonical merge result, any case where the
canonical merge rejects a delta still forwards that delta to every subscriber.
That's fine for a proper CRDT join where everyone runs identical merge
semantics — which is exactly what's currently not true.

## 3. The "complete side wins" rule breaks convergence (logical bug)

The rule at `crdt/merge.go:99-105` (mirrored in `merge.ts`) decides cell
conflicts using **fill-level** state, and the merged output then sets
`complete = l ∨ r`. That makes the merge non-associative: cells absorbed from a
*non*-complete side into a merge with a complete side get "blessed" and later
win conflicts they shouldn't. Example with fills a, b, c where only b is
complete and cell 5 exists in a (clock 10, "X") and c (clock 20, "Y") but not
in b:

- `merge(merge(a,b), c)`: cell 5 = "X" joins a complete fill uncontested, then
  beats c's higher-clock "Y" via the complete rule.
- `merge(a, merge(b,c))`: "Y" joins the complete fill, then beats "X".

Different merge orders → different converged states, which defeats the CRDT
guarantee. The underlying intent ("a solved puzzle's cells are correct, keep
them") would be better expressed per-cell — e.g. when a client completes the
puzzle, mark its cells `CHECKED_RIGHT`, and let the existing checked-wins rule
(which *is* convergent) do the work — rather than a fill-level flag influencing
cell conflicts.

Note the test suite wouldn't catch this: `runOne` tests two-way orders and
idempotence, but the counterexample needs a three-way merge where completeness
differs.

## 4. `checkAnswers` re-asserts cell content at a fresh clock (logical bug, minor)

`checkAnswers` (`crossword.ts:693-701`) sends each checked cell's *current
fill* with a new clock `g.clock+1`. Semantically a check is a read-only
annotation, but as implemented it's a write: checking a wrong letter can
clobber a concurrent correction from another player (the check's fresh clock
wins LWW, re-installing the wrong letter, now flagged `CHECKED_WRONG`). Reveal
legitimately writes content; check shouldn't.

## 5. Smaller divergences and nits

- **Duplicate-node handling differs**: Go errors on a duplicate node in the
  left fill (`merge.go:38`); TS silently dedups both sides. Only matters for
  malformed input, but it's an input-dependent behavioral divergence between
  the two implementations — and per finding 1, a Go-side merge error is
  currently a server panic.
- **`mergeFill` lacks the owner bounds check** both real merges have —
  `fill.nodes[cell.owner]` on a bad index yields `undefined` and silently
  miscompares rather than throwing.
- **`s.repo.UpdateGame(game.game)` error is ignored** (`server.go:181`) — a
  failed persist is silent; the canonical in-memory fill and the database
  diverge until restart, when the game silently rolls back.
- **Per-client merge errors only log** (`server.go:188`) — that client silently
  never receives the delta. Mostly unreachable since the canonical merge would
  have errored first, but worth a comment or a disconnect.
- **The server trusts `complete=true` from clients** (`updateGame` sets it, but
  nothing verifies). Any client can send `complete=true` without solving,
  freezing contested cells via the complete-wins rule. The server has the
  puzzle solution and could validate. (Not deployed today, but it compounds
  finding 3.)
- **Cross-language test vectors have a hidden ordering dependency**: the Go
  test *writes* the `.dat` files (`merge_test.go:30`) that the TS test reads
  through the `testdata` symlink. Edit a `.json` and run only the TS tests, and
  they silently validate stale vectors. Consider a generator step or checking
  the `.dat` files in.
- **RPC side effect inside a React `setState` updater** (`puzzle.tsx:62-81`):
  updaters should be pure; under StrictMode dev double-invocation this fires
  duplicate `updateFill` calls. Harmless today because merges are idempotent,
  but fragile.

## Priority

Findings 1 and 2 first: one is a remotely-triggerable crash, and the other
means the actual deployed merge semantics on the client are not the designed
CRDT — the carefully mirrored `merge.ts` is currently dead code.
